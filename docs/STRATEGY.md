# HiveMind-UI — 戦略 / Strategy

> **EN TL;DR** — HiveMind-UI replaces qualitative UX research with three Grok-driven
> phases: personas generated from what X is saying *today* (X Search), those personas
> driving a real browser with faithful confusion and rage-quits, and an interview-style
> debrief written from the behavior log. Go-to-market: viral "rage-quit" replay GIFs on X
> (Build in Public), an LP-testing tool for X advertisers, and an open repo that makes the
> claim "this only works with Grok" demonstrable rather than asserted. Full argument below
> in Japanese, since this is the pitch we actually deliver.

## 1. 何を置き換えるのか

現在の定性UXリサーチは、こうなっています。

| 工程 | 現状 | 期間 | コスト |
| --- | --- | --- | --- |
| モニター募集 | パネル会社に依頼、属性指定 | 1〜2週間 | 1人 5,000〜20,000円 |
| スクリーニング | 属性・ITリテラシーの確認 | 数日 | 工数 |
| 実施 | 1人30〜60分、モデレーター同席 | 数日〜2週間 | モデレーター工数 |
| 分析 | 録画を見て発話を書き起こし、KJ法 | 1〜2週間 | 研究者工数 |
| **合計** | | **3〜6週間** | **数十万〜数百万円** |

この間、LPは改善されず、広告費は回り続けます。10人テストして「分かりにくい」と言われる
だけの結論に、1ヶ月半かかる。これが業界の標準です。

HiveMind-UIが置き換えるのはこの一式です。人間のテスターを**採用**する代わりに、
**今日のXから人格を生成**し、**その人格として実際のブラウザを操作**し、
**インタビュー形式のレポート**まで数分で出します。

重要なのは「速い」だけではないという点です。人間のモニターは、募集した時点の
**静的な属性**（30代・女性・ITリテラシー中）しか持ちません。HiveMind-UIのペルソナは
**今朝のニュース、今日のトレンド、現在の感情**を持ちます。LPが刺さるかどうかは、
属性ではなく「今その人が何を考えているか」で決まります。

## 2. なぜGrokでしか成立しないか

このプロダクトの中心的な主張は「**Grokでしか成立しない**」。それを3点で示します。

### 2.1 鮮度がプロダクトそのもの

静的ペルソナと動的ペルソナの差は、機能差ではなく**品質差**です。

- 学習データで作ったペルソナ → 「30代・共働き・時短志向」。どこにでもある。無味乾燥。
- 今朝のXから作ったペルソナ → 「今朝の物価高報道を見て、家計簿アプリを開いた直後。
  外食をやめたところで、銀行の手数料にも敏感になっている」。

後者を生成するには、**リアルタイムのX検索**が必要です。Web検索でも代替できません。
Xの投稿には、感情・スラング・現在の不満が、その日の解像度で書かれているからです。
これは、X Search（`x_search`）がファーストパーティで使えるGrokだけが持つ入力です。

### 2.2 ペルソナの「根拠」が提示できる

HiveMind-UIのペルソナは `x_signals` を持ちます。`insight`（何を読み取ったか）と
`evidence`（実際の投稿の要旨・ハンドル）です。つまり

> 「この離脱は、今朝のXのこの投稿と同じ温度のユーザーで再現しました」

と、**根拠つきで**言えます。モックモードでは絶対に作りません（`generated_by: mock` を必ず明記）。
逆に言えば、根拠を出すためにXの検索結果をそのまま受け取れるモデルが必要で、それがGrokです。

### 2.3 Computer Use的な操作と分析を1つのモデルで

フェーズ2（操作の意思決定）とフェーズ3（主観レビュー）は、**同じ人格の一貫性**を
必要とします。操作中に「分からない」と叫んだ人が、レポートで急に冷静なUX専門家に
なってはいけません。

すべてのフェーズを1モデル（`grok-4.7`）で通すことで、口調・語彙・不満が保たれます。
プロンプト層（`hivemind/prompts.py`）は分離してあるのでドライバの差し替えは可能ですが、
**現時点でこの一貫性を保ったまま最後まで通せる構成**が、Grok × Computer Useです。

## 3. 労働の自動化という価値

### 3.1 何が自動化されるのか

| 人間がやっていたこと | HiveMind-UIでどうなるか |
| --- | --- |
| モニターの募集・調整 | 不要（ペルソナ生成） |
| モデレーターが横で誘導 | 不要（自律操作） |
| 「今どう思いました？」と聞く | 不要（心の声を毎ステップ記録） |
| 録画を見て発話を書き起こす | 不要（`log.jsonl` が元から構造化データ） |
| KJ法でまとめる | 不要（`cohort_report.md` を自動生成） |
| 「なぜ離脱したか」を推測 | 離脱理由が記録されている |

### 3.2 「推測」が「記録」になる

これが実務上いちばん効きます。人間のテストでも、離脱の**理由**は推測です
（「たぶん分かりにくかったのだろう」）。HiveMind-UIでは、離脱した瞬間の心の声が
`log.jsonl` に残っています。

```
step 12 give_up [angry] もう無理。このサイト、ユーザーのこと何も考えてない。
  → reason: 「振込」の入口が3画面先で、ITリテラシー0.16の被験者は到達できなかった
```

改善会議で「たぶん」が消えます。

### 3.3 コスト構造

人間100人のテストは、**線形に**コストが増えます。HiveMind-UIは、1セッションあたり
数十円〜数百円（モデルのトークン＋X Searchの投稿課金）です。しかも
`usage.json` に1回ごとの呼び出し回数とトークン数を記録しているので、
「この検証にいくらかかったか」を事後に説明できます。広告費と同じ感覚で、
**検証にも予算を割ける**ようになります。

## 4. スケーラビリティ

### 4.1 いまの実装

現状はコホートを**逐次実行**しています（1人ずつ）。理由は、ログが読みやすく、
`--speed` のデモが成立し、1人の失敗が他に波及しないことです。ボトルネックは明白で、
Playwrightのコンテキストを1つずつしか使っていない点です。

### 4.2 スケールの道筋

| 段階 | 構成 | 想定 |
| --- | --- | --- |
| 現在 | 逐次、1ブラウザ・プロセス | 3〜10体。デモと検証 |
| 次 | 非同期Playwright、ワーカーごとに1コンテキスト | 100体。実務投入 |
| 将来 | ヘッドレスコンテナの水平展開 | 1,000体以上。A/B比較の常用 |

「コンテキストの異なる100体」は**数分**で終わります。人海戦術で同じことをやると
数週間かかる。ここが投資対効果の核心です。

### 4.3 コストが線形でも意味がある理由

モデル呼び出しは線形に増えますが、**人間のリードタイムは消える**。
そして重要なのは、100体のうち90体が同じ摩擦点で離脱するなら、90体を実行する必要は
なかったかもしれない、という発見が得られることです。**規模は網羅のためではなく、
分布を見るため**に使います。

## 5. GTM（市場への出し方）

3本柱でいきます。優先順位は ①→② で、①は②の集客装置です。

### ① バイラルデモ（X上の「キレて離脱するAI」）

「Grokが生成したペルソナが、その人格になりきって1998年風の銀行サイトを操作して、
キレて離脱する」というGIFをXに投稿します。詳細は [6章](#6-バイラルデモの設計)。

### ② X広告主向けLP検証ツール

出稿前に「今バズっている層にLPが刺さるか」を検証する。詳細は [7章](#7-x広告主向けツールとしてのlp検証)。

### ③ Build in Public

コードもプロンプトも公開し、指標を公開しながら進めます。詳細は [8章](#8-build-in-public-の進め方)。

### なぜX起点なのか

- プロダクトの入力（X Search）と出力（GIF・レポート）が、両方X上で完結する。
- X広告主という**支払い意欲が明確な**顧客層が、そのままXの中にいる。
- xAIのエコシステムの上に乗ることで、技術的な正当性と注目を同時に得られる。

## 6. バイラルデモの設計

`make viral`（`demo_tools/viral_demo.py`）が、seed固定のオフラインコホートを回し、
以下を自動生成します。

- `sessions/p*/replay.gif` — カーソルが動き、字幕で心の声が出るGIF
- `x_post.md` — 日本語・英語の投稿文面（実測値入り）

投稿文面には、実測値だけが入ります（捏造ゼロ）。

```
本日の被験者: 洋子（68・IT慎重シニア）
結果: 離脱｜滞在 47秒｜迷い 12.4秒｜怒りクリック 2回
「もう無理。このサイト、ユーザーのこと何も考えてない。」
```

### 刺さる理由

1. **人格が具体的。** 「68歳・IT慎重シニア」が本当に迷い、本当にキレる。
   GIFに映る挙動が、その属性の人間の挙動として説得力を持つ。
2. **失敗が見える。** 成功デモは刺さらない。**キレて離脱する**ことがコンテンツになる。
3. **自分のサイトで試せる。** リポジトリが公開されているので、視聴者は自分のLPで
   すぐ再現できる。反応が「へえ」で終わらず、**行動**に変わる。
4. **主張の証明になっている。** 「Grok × Computer Useでしかできない」という主張が、
   投稿1本で体験される。広告ではなくデモが論証になる。

## 7. X広告主向けツールとしてのLP検証

### 課題

X広告のLPは、出稿してから結果が分かります。CVRが悪い理由は「属性が違う」のか
「LPが分かりにくい」のかが区別できず、広告費を燃やしながら学ぶことになります。

### 提供

```
その日のXの空気でペルソナを生成
  → そのLPを20体のペルソナが踏む
  → 「どの感情層がどこで離脱したか」+ 改善案
```

- **属性ではなく感情で切る。** 「家賃に不満な20代」は、広告のターゲティングでは
  作れない切り口です。Xの会話からなら作れます。
- **離脱理由が記録される。** 改善案（`cohort_report.md` の Recommendations）が
  そのまま次のクリエイティブ制作の入力になります。
- **出稿前のA/B。** 旧LPと新LPを同じコホートで走らせ、離脱箇所の差を見ます
  （`samples/retro_bank.html` と `samples/modern_bank.html` がその雛形）。

### 課金の考え方

| | 内容 | 課金 |
| --- | --- | --- |
| Self-serve | リポジトリを自分で回す | 無料（モデル費用は自腹） |
| Managed | コホート設計＋レポート納品 | コホート単位 |
| Ads bundle | 出稿パッケージに検証を同梱 | 広告費連動 |

最初の顧客は、**X広告を出している企業のマーケター**です。彼らはすでにLPの
改善に予算を持っており、`usage.json` で費用を説明できることを価値として理解します。

## 8. Build in Public の進め方

- **コードを公開する。** プロンプト（`hivemind/prompts.py`）も公開します。
  「何をどう指示しているか」が検証対象になることが、この種の主張の信頼につながります。
- **失敗も公開する。** 「低リテラシーのペルソナが最後まで離脱しなかった」という
  モデルの失敗をリポジトリのテストとして記録しています。改善の履歴が資産です。
- **数値を公開する。** 完了率・離脱理由・怒りクリックはログから計算した実測値です。
  良く見せるための調整をしません（`generated_by: mock` の明記も同じ理由）。
- **リポジトリを導線にする。** 投稿の最後は常に「あなたのサイトでも試せる」。

公開によって得たいのは、次の3つです。

1. **反応の速いフィードバック。** どのペルソナが刺さるかが、投稿の反応で分かる。
2. **技術的な正当性。** 再現可能な形で出ていること自体が、主張の裏付けになる。
3. **人材と顧客の流入。** この手法を試したいマーケターと、一緒に作りたい開発者。

## 9. 指標

| 種別 | 指標 | 定義 |
| --- | --- | --- |
| プロダクト | 完了率 | `outcome == completed` の割合（ログから計算） |
| プロダクト | 平均迷い時間 | `hesitation_ms` の平均（`sim_ms` 基準） |
| プロダクト | 怒りクリック数 | 連続する `angry` クリック（ログから計算） |
| プロダクト | 離脱理由の分布 | `drop_reasons` ヒストグラム |
| 事業 | 検証1件あたりの時間 | 依頼から `cohort_report.md` 納品まで |
| 事業 | 検証1件あたりのコスト | `usage.json` の合計 |
| 認知 | デモ投稿の反応 | 保存・引用・「自分のサイトで試した」数 |
| 認知 | リポジトリ流入 | デモ投稿経由のクローン数 |

**見てはいけない指標**: 「ペルソナの数」。増やすこと自体は価値ではありません。
分布が見えて初めて価値です。

## 11. リスクと正直さの設計

| リスク | 対応（実装済み） |
| --- | --- |
| ペルソナの根拠が嘘になる | モックでは必ず `generated_by: mock` を明記。Grokモードでも `evidence` は検索結果のみ |
| 統計値をモデルが捏造する | 完了率・迷い時間・怒りクリックは**ログから計算**。モデルは文章だけを書く |
| 「都合よく失敗させている」と言われる | seed固定で再現可能。同じ入力なら同じ結果。テストで統計的に検証 |
| 過剰な約束になる | 「人間のテストを置き換える」ではなく「人間のテストの前段を自動化する」と表現する |
| 対象サイトへの負荷・規約 | 対象は**自社のLP**を前提とする。第三者サイトへの無断実行は想定しない |
| モデル費用の不透明さ | `usage.json` に呼び出し回数・トークン・取得投稿数を記録し、検索窓とターン数を設定で制限 |

この表の左側は、いずれも**「盛れば伸びる」誘惑が働く項目**です。だからこそ、
正直さを設計に埋め込んでいます。この種のプロダクトで一度でも数字を盛れば、
**デモそのものが信頼を失い、プロダクトの根拠が消えます**。
